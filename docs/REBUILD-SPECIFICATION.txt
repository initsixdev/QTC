IMPORTANT SOURCE STATUS

There are two different “latest versions”:

Latest recoverable source version:
QTC Terminal 2.3.1

Latest delivered and used binary:
QTC Terminal 2.6.0

Versions after 2.3.1 were delivered as working standalone binaries, but their exact matching source trees were not preserved. Their behavior and intended implementation are documented here so the application can be rebuilt from the 2.3.1 source.

The next proper release should be QTC 2.6.1 or QTC 2.7.0, depending on whether the reconstruction is treated as a patch or a new source-backed release.

1. PROJECT PURPOSE

QTC is a terminal-based desktop messenger for MeshCore companion radios.

Its goals are:

* Connect to a MeshCore companion radio through USB serial.
* Send and receive direct messages.
* Send and receive channel messages.
* Store message history locally.
* Recover messages that arrived while the terminal UI was closed.
* Highlight unread conversations.
* Organize channels, favorites, contacts, and network nodes clearly.
* Provide Linux desktop notifications.
* Provide notification sounds.
* Keep the radio connected in the background.
* Allow the terminal UI to disconnect and reconnect without releasing USB.
* Provide private-channel management directly inside QTC.
* Avoid forcing normal users to understand channel slots, raw hexadecimal keys, packet routing internals, and other low-level radio details.
* Remain lightweight and usable entirely from a terminal.

4. USB AND SERIAL ACCESS

QTC connects to serial devices such as:

/dev/ttyACM0
/dev/ttyUSB0

Device listing command:

qtc --list-devices

A Linux user may need membership in the serial-access group:

sudo usermod -aG dialout "$USER"

The user must completely log out and log in again after changing group membership.

QTC also supports printing an appropriate udev rule:

qtc --print-udev-rule

Example installation:

qtc --print-udev-rule | sudo tee /etc/udev/rules.d/99-qtc-meshcore.rules
sudo udevadm control --reload-rules
sudo udevadm trigger

The radio should then be unplugged and reconnected.

5. FUNCTIONALITY PRESENT IN THE 2.3.1 SOURCE BASELINE

QTC 2.3.1 is the latest recoverable source-backed version.

5.1 Direct messaging

Implemented functionality includes:

* Sending direct messages.
* Receiving direct messages.
* Selecting a contact and opening its conversation.
* Local message history.
* Unread-message state.
* Message timestamps.
* Retry handling.
* Message identity preservation across retries.
* Duplicate-message suppression.
* Clean serial shutdown.

A previously observed problem was that a sent message could appear two or three times on the receiving side.

The intended correction was:

* Generate or retain one stable message identity.
* Do not assign a new identity during a retry.
* Check received message identifiers before inserting.
* Ignore a message that already exists in the local database.
* Avoid treating a retransmission as a separate message.

5.2 Channel messaging

QTC can:

* Display channels already configured on the radio.
* Receive messages from those channels.
* Send messages to those channels.
* Store channel history.
* Track unread channel messages.
* Pin joined channels above contacts.

At the 2.3.1 source stage, channel creation and key management were not yet fully available through the QTC interface.

5.3 Message recovery

QTC polls the connected radio for waiting messages.

The intended recovery process is:

1. QTC connects to the radio.
2. QTC asks the radio for pending or stored messages.
3. Received messages are normalized.
4. Existing message identifiers are checked.
5. New messages are inserted into SQLite.
6. Conversations are marked unread when appropriate.
7. Notifications are emitted if enabled.

This allows QTC to recover messages sent while the terminal program was not running, subject to what the radio and MeshCore protocol retain.

5.4 Local database

SQLite stores:

* Contacts
* Contact aliases
* Messages
* Channel history
* Unread state
* Settings
* Favorite state
* Favorite groups
* Device configuration
* Notification configuration
* Sound configuration

Database migrations must preserve existing data.

5.5 Linux desktop notifications

QTC supports notifications through:

notify-send

Notification test command:

/testnotify

The application must not crash when notify-send is unavailable.

Expected behavior while the terminal UI is detached:

* Incoming messages continue to be received.
* Incoming messages continue to be stored.
* Desktop notifications continue to be shown.
* Notification sounds continue to play when enabled.

5.6 Notification sounds

QTC supports notification sounds using available Linux sound helpers.

PipeWire playback through pw-play is preferred when available.

The application should handle:

* Sound enabled
* Sound disabled
* Sound player missing
* Sound file missing
* Background core running without an attached terminal
* Terminal UI connected

A sound failure must never interrupt receiving or storing messages.

6. CONTACT SEARCH

Contact search supports substring matching.

For example, searching for:

branimir

should match:

HR OS Branimir Bla
Branimirovski

Plain text behaves conceptually like:

*branimir*

Supported wildcard characters:

* means zero or more characters
  ? means exactly one character

Examples:

HR*Bla
Branimir?vski

Controls:

/ begins or edits search
Esc clears search

Command equivalents:

/search branimir
/clearsearch

Search must also work when the terminal delivers pasted text in a single input event instead of one character at a time.

Unread conversations are visibly highlighted.

Expected rules:

* Unread channels are promoted inside the Channels section.
* Unread favorites are promoted inside their favorite group.
* Unread ordinary contacts are promoted only inside the same route-distance group.
* Moving the selection over a contact does not clear unread state.
* Opening a conversation clears its unread state.
* Unread state survives terminal detach and reconnect.
* Background messages update unread state while no UI is attached.

10. QTC 2.3.2: SIDEBAR SCROLLING CORRECTION

The initial pinned-sidebar implementation caused the entire sidebar to behave as if it were pinned.

QTC 2.3.2 corrected contact scrolling.

Expected behavior:

* Channels remain pinned.
* Favorites remain pinned.
* CONTACTS heading remains pinned.
* Contacts scroll.
* Up and Down move the selection.
* j and k move the selection.
* The viewport follows the selected contact.
* Resizing the terminal recalculates the available contact area.
* Search results use the same scrolling area.

The earlier bug was caused by layout logic that searched rendered text to locate the Contacts section and used an incorrect string length.

That approach must not be reused.

The rebuilt version should use explicit layout state such as:

* Number of pinned rows
* Row containing the Contacts heading
* First row of the contact viewport
* Contact viewport height
* Contact scroll offset
* Selected contact index

The UI must never depend on finding a literal label such as CONTACTS inside already rendered output.

11. CONTACT ROUTE ORDERING

Normal person contacts are ordered by route proximity.

Expected order:

direct
1 hop
2 hops
3 hops
additional hop groups
flood

The term unknown route was replaced with flood in the user interface.

The internal state may still use a value such as route_unknown or route_known false, but the visible label should be flood.

Expected display:

-- flood --

Ivan
flood // heard 3h ago

Recommended contact structure:

* Contact ID
* Node type
* Route hop count
* Whether a learned route is known
* Unread state
* Favorite state
* Last-heard timestamp
* Display name

Recommended ordinary-contact sorting:

1. Person contacts only
2. Known route before flood
3. Lower hop count first
4. Unread first within the same hop count
5. Most recently heard
6. Case-insensitive display name
7. Contact ID as a final stable tie-breaker

Favorites are rendered separately in the pinned Favorites section.

14. QTC 2.5.0: PERSISTENT BACKGROUND CORE

QTC 2.5.0 introduced persistent background operation.

The user confirmed that this behavior worked well.

14.1 Normal startup

Running:

qtc

should:

1. Check whether a QTC background core is already running.
2. Connect to it when available.
3. Start it automatically when unavailable.
4. Wait for the local socket to become ready.
5. Attach the terminal interface.

The user should not need to manually start a daemon during normal use.

14.2 Disconnecting the terminal UI

Expected controls:

F8
Ctrl+C
/disconnect

Disconnect means:

* Close only the current terminal interface.
* Keep the background core running.
* Keep the serial device open.
* Keep USB ownership.
* Continue polling the radio.
* Continue receiving messages.
* Continue storing messages.
* Continue retrying sends.
* Continue desktop notifications.
* Continue notification sounds.

Running qtc again should reconnect to the existing background core.

14.3 Full shutdown

Expected controls:

Ctrl+Q twice within a short timeout
/shutdown
/quit

Full shutdown means:

* Stop accepting new user sends.
* Finish or persist active operations safely.
* Flush SQLite writes.
* Stop radio polling.
* Close the serial device.
* Close client sockets.
* Remove the Unix socket.
* Remove lock and PID state.
* Release USB.
* Terminate the background core.

14.4 Recommended architecture

The application remains one executable but supports multiple internal roles.

QTC background core responsibilities:

* Own the USB serial connection.
* Handle MeshCore protocol traffic.
* Poll waiting messages.
* Store messages.
* Deduplicate messages.
* Manage send queues and retries.
* Run desktop notifications.
* Run notification sounds.
* Manage channel operations.
* Serve local terminal clients through a Unix socket.

QTC terminal client responsibilities:

* Connect to the local background core.
* Receive state snapshots and events.
* Render the terminal interface.
* Send user actions to the core.
* Detach without closing USB.
* Restore terminal state cleanly on exit.

Recommended Unix socket:

$XDG_RUNTIME_DIR/qtc/qtc.sock

Fallback:

/tmp/qtc-$UID/qtc.sock

The runtime directory and socket must:

* Be owned by the current user.
* Use restrictive permissions.
* Reject access from other users.
* Be cleaned up safely after crashes.

14.5 Single-instance protection

Only one QTC core may own:

* The selected serial device
* The active profile database
* The runtime Unix socket

The implementation should use:

* A Unix socket
* A user-owned lock file
* Stale socket detection
* Safe PID verification
* Process ownership checks

QTC must never kill a process based only on an unverified stale PID file.

14.6 Local client protocol

The core and terminal client should exchange structured messages.

They should not exchange already-rendered terminal screens.

Suggested frame structure:

* Four-byte payload length
* One-byte message type
* Payload

Suggested message types:

HELLO
STATE_SNAPSHOT
CONTACTS_CHANGED
CHANNELS_CHANGED
MESSAGES_CHANGED
SEND_MESSAGE
MARK_READ
SET_FAVORITE
SET_FAVORITE_GROUP
CHANNEL_CREATE
CHANNEL_JOIN
CHANNEL_INVITE
CHANNEL_ROTATE
CHANNEL_LEAVE
SHUTDOWN

The background core should be the sole SQLite writer.

This prevents multiple UI clients from writing conflicting database state.

15. QTC 2.6.0: FIRST-CLASS PRIVATE CHANNEL MANAGEMENT

QTC 2.6.0 introduced a first-class Channels page.

Entry points:

Expected page:

Family, private

Actions:

15.1 Create private channel

The ordinary Create workflow should ask only for:

Channel name

QTC should then:

1. Find a free radio channel slot.
2. Generate a secure 16-byte random key.
3. Write the channel configuration through the background core.
4. Refresh the channel list from the radio.
5. Add the channel to the pinned Channels section.
6. Generate a standard MeshCore invitation.

Users should not normally be asked to:

* Select a numeric slot
* Generate hexadecimal manually
* Use OpenSSL
* Shut down QTC
* Run meshcli

Slot selection and raw-key entry may remain available inside an Advanced flow.

Secure key generation should use a cryptographic operating-system source, such as getrandom or securely reading /dev/urandom.

15.2 Join private channel

Pressing capital J opens the Join flow.

The main workflow accepts a complete invitation such as:

meshcore://channel/add?name=Family&secret=...

An Advanced form may accept:

Name
32-character hexadecimal key

Validation must reject:

* Empty name
* Malformed URI
* Missing secret
* Invalid hexadecimal
* Key that does not decode to exactly 16 bytes
* No free channel slot
* Accidental replacement of an existing channel
* Duplicate channel without explicit confirmation

The 2.6.0 Join flow worked when capital J was pressed, but the active text input was not obvious enough.

The rebuilt version should show a real Join dialog with:

* A visible input field
* A clear description of accepted input
* Validation errors inside the dialog
* Stable input while background events arrive
* No blinking or full-screen redraw while typing

15.3 Rotate channel key

Private MeshCore channels do not provide a centralized member list or server-side member removal.

Anyone with the current channel key can read and send channel messages.

To remove access from someone, the remaining members must rotate the key.

Rotate should:

1. Name the selected channel.
2. Explain that old invitations will stop working.
3. Require explicit confirmation.
4. Generate a new secure key.
5. Update the radio configuration.
6. Refresh the channel list.
7. Generate a new invitation.
8. Allow the new invitation to be sent to trusted contacts.

15.4 Leave channel

Leave should:

* Name the selected channel.
* Require confirmation.
* Clear the channel slot on the radio.
* Refresh the channel list.
* Remove the channel from the pinned Channels section.
* Preserve or explicitly handle local historical messages according to a defined policy.

The safest default is to preserve historical messages locally while removing the ability to receive future messages.

17. KNOWN QTC 2.6.0 ISSUES

17.1 Join input was unclear

Capital J opened the Join workflow, but the transition into input mode was visually unclear.

The fix is a dedicated modal form rather than silently pre-filling the general command line.

17.2 Invite action was incomplete

Pressing i should not primarily display a raw invitation for copying into an external application.

The default should be sending the invitation directly to selected MeshCore contacts.

Copy invitation should remain available as a secondary action.

17.3 Channels-page jitter

The Channels page visibly blinked or jittered.

The likely cause was complete terminal repainting on every daemon poll, even when no visible channel state changed.

* Other clients can display the standard URI.
* The receiver can copy the URI manually if their client lacks QTC integration.
* No external messaging service is required.
* The invitation uses the existing MeshCore direct-message route.

19. CHANNELS-PAGE JITTER FIX

The Channels page must not repaint on every background polling cycle.

The terminal UI should track visible revisions and redraw only when something visible changes.

Recommended render state includes:

* Current page
* Terminal width
* Terminal height
* Selected row
* Scroll offset
* Modal state
* Input text revision
* Channel revision
* Contact revision
* Message revision
* Visible connection-state revision

A redraw should happen only when:

* The page changes.
* Terminal dimensions change.
* Selection changes.
* Scroll position changes.
* Modal state changes.
* Input text changes.
* Channel data changes.
* A visible connection indicator changes.
* A notification or status line displayed in the UI changes.

A radio poll that returns no visible change should cause zero terminal writes.

19.1 Buffered rendering

The complete visible frame should be rendered into memory and written in one operation or a very small number of operations.

The code should avoid:

* Clearing the screen on every poll
* Printing each row with a separate printf
* Moving the cursor repeatedly while asynchronously processing input
* Repainting static headings unnecessarily
* Letting background events overwrite modal forms

19.2 Cursor handling

During a redraw:

* Hide the cursor.
* Render the full changed frame.
* Restore the cursor at the correct input location.
* Show the cursor again.

The cursor must remain stable while entering:

* Channel name
* Invitation URI
* Raw key
* Contact search
* Confirmation input

19.3 Revision handling

The daemon should increment a channel revision only when channel state actually changes.

Receiving an unchanged response from the radio should not increment the revision.

The UI should compare the last rendered revision with the current revision.

25. COMPILER AND SANITIZER REQUIREMENTS

Normal warning flags:

-Wall
-Wextra
-Wpedantic
-Werror

Sanitizer testing:

-fsanitize=address,undefined

Recommended hardening where compatible:

-fstack-protector-strong
-D_FORTIFY_SOURCE=2

Release builds should use explicit and recorded optimization flags.

The exact compiler version, flags, linker version, and target must be recorded in the release manifest.

A binary must never again be released without preserving its exact source.

27. SUGGESTED VERSIONING

Because QTC 2.6.0 existed as a binary but its exact source was not preserved, there are two reasonable choices.

Option A:

Rebuild the intended 2.6.0 behavior and release the repaired version as QTC 2.6.1.

Advantages:

* Maintains continuity with the delivered binary.
* Clearly communicates that this is a corrected version.
* Matches the existing feature history.

Option B:

Release the fully reconstructed source-backed version as QTC 2.7.0.

Advantages:

* Makes it clear that this is a newly reconstructed and reproducible baseline.
* Avoids pretending that the reconstructed internals are identical to the lost 2.6.0 source.
* Allows architectural cleanup during reconstruction.

Recommended choice:

Use QTC 2.7.0 for the first fully reconstructed, source-backed release.

The release notes can state:

* Reconstructs features delivered in binary-only releases 2.3.2 through 2.6.0.

30. FINAL PROJECT DIRECTION

QTC should remain a lightweight terminal application, but it should behave like a proper modern messenger rather than a thin serial console.

The core product principles are:

* Messaging terminology before radio jargon.
* Safe defaults.
* No accidental sharing of private channel keys.
* No unnecessary external messaging applications.
* Persistent background receiving.
* Clear separation between people and network infrastructure.
* Stable, non-flickering terminal rendering.
* Full functionality without requiring meshcli for ordinary workflows.
* Local-first storage.
* Clean shutdown.
* Reproducible builds.
* Matching source for every binary.

The most important technical correction is restoring a reproducible, source-controlled release process.

The most important user-facing correction is completing private-channel invitations safely inside MeshCore, with an explicit recipient confirmation and Cancel selected by default.
